## 修复 16KB 页对齐不合规（用户报 APK 警告）

### 根因
用户报 6 个 .so 未 16KB 对齐（libavcodec/avdevice/avfilter/avformat/avutil/libc++_shared）。
全部来自 `com.arthenica:ffmpeg-kit-full-gpl:6.0-2` —— 原版用旧 NDK 编的，只有 4KB 对齐。
Chaquopy 的 libpython3.10.so 等本来就是 16KB 对齐的，无需处理。

### 解决
换依赖：`dev.ffmpegkit-maintained:ffmpeg-kit-full:8.1.9`（社区维护版，NDK r27c 编，
`-Wl,-z,max-page-size=16384`，Maven Central 正常可拉）。
**包名仍是 com.arthenica.ffmpegkit，Kotlin 代码一行没改**（编译通过即证明 API 兼容）。
选 LGPL 的 full（非 -gpl）：我们只用 pcm_s16le / aac / amix / alimiter / -c:v copy / ffprobe。

### 16KB 合规要查两层（本机已全部通过）
1. ELF：PT_LOAD 的 p_align >= 0x4000 且 p_offset ≡ p_vaddr (mod 0x4000)
2. ZIP：STORED 的 .so 在包内偏移 % 16384 == 0（AGP 8.5.1+ 自动做，本机 8.7.3 已生效）

### 固化产物
`android/check_16kb.py`：纯标准库（无需 NDK/readelf，Windows 可跑），
同时查 ELF + ZIP 两层，退出码 0/1。
**坑**：算 .so 数据偏移必须用 zip「本地头」的 nlen/elen（偏移 26/28），
不能用 ZipInfo.extra（那是中央目录的 extra，长度不同，会误报 4KB 未对齐）。
官方交叉验证：`zipalign -c -P 16 -v 4 app.apk`（注意 -P 后还要跟 <align> 参数，通常 4）。

### 结果
重新 assembleDebug → BUILD SUCCESSFUL，APK 165MB，38 个 .so 两层全部 16KB 对齐。
文档已同步：README.md 新增「七、16KB 页对齐」章节，排错表加两条。

## 修复真机报错：ProgressSink is not callable（Chaquopy 跨语言坑）

### 报错
`PythonEngine$ProgressSink is not callable because it implements no functional interfaces`

### 根因（重要，以后别再踩）
Chaquopy 给**所有** Java 对象都挂了 Python 的 `__call__`，
所以 `callable(java_object)` 恒为 True；但该对象只有在类实现了
「函数式接口」（只有一个抽象方法的接口）时才真的能被调用，
否则在**调用那一刻**才抛 TypeError。
原 `mobile_api._make_progress_callback` 先判 `callable()` 就原样返回，
于是把 Java 对象当函数调用 → 崩。

### 修复（两层）
1. `mobile_api._make_progress_callback`：**先**按方法名
   `onProgress / on_progress / onEvent` 识别并包一层闭包，**再**判 callable。
   另加 `_safe_callback`：回调内部抛异常只打 traceback 不中断主流程
   （进度上报失败不该让几分钟的任务挂掉）。
2. `PythonEngine.ProgressSink` 改为实现 `fun interface PythonProgress`
   （SAM = onProgress(PyObject?)），这样即使有别的路径 `obj(...)` 也能通。

### 回归测试
新增 `backend/tests/test_progress_callback.py`，用 FakeChaquopyObject
（callable()==True 但调用抛 TypeError + 有 onProgress）复现现场，
15 项断言全过；已加进 `tests/run_all.py`。
四项后端测试全 PASS，对齐误差仍 0.0000s。
重新 assembleDebug → BUILD SUCCESSFUL，16KB 两层仍全绿。

## 定位：选了 mp3 却变成 .mp4（SAF 扩展名推断 bug）

`MainActivity.guessExtension()`（第 236-240 行）用 `uri.lastPathSegment` 取扩展名，
但 SAF 的 content:// URI 常是 `document/1234` 这类纯数字 ID，取不到后缀，
于是走兜底 `else ".mp4"` —— 音乐文件被复制成 `input_music.mp4`，
后端 `mobile_api._check_ext(SUPPORTED_AUDIO_EXT)`（第 205 行）直接拒。
正解：先查 `OpenableColumns.DISPLAY_NAME`，再用 `contentResolver.getType()` + MimeTypeMap，
音频兜底 `.mp3`；或由调用方传 defaultExt（视频 .mp4 / 音乐 .mp3）。
（用户已自行改好，MainActivity 239-256 行。）

## 修复：cannot convert list object to java.util.List

`FfmpegBackend.execute(args: List<Any?>, timeout: Double)` 被 Python 调用时崩。
**Chaquopy 不做 Python list → java.util.List 的隐式转换**（反向 Java List → Python 可以）。
唯一从 Python 往 Java 传 list 的地方就是它（probe 只传 str）。
改为 `execute(args: PyObject, timeout: Double)`，内部 `args.asList().map { it.toString() }`。
**规则：跨语言边界收集合一律用 PyObject 自己遍历，别写 List/Array 参数。**
改完 assembleDebug BUILD SUCCESSFUL，APK 165MB。

### 修「一直在加载页面」（真机反馈）

### ❗自己引入的严重 bug（已修，务必别再犯）
给 file input 加兜底时，把 `patchFileInput()` 放在 `if (!window.__syncStageBridgeReady)` 的
整体早退**后面**。注入时机是 `onPageStarted` + `onPageFinished` 两次：
onPageStarted 时 DOM 还没解析完 → `getElementById` 返回 null → patch 跳过，
但守卫已经置位 → onPageFinished 再注入被直接 return → **兜底永远装不上**，
